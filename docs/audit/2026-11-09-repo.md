## Other findings

### F1 `delve.start` accepts malformed commands

- **Rework if left:** medium
- **Effort:** S
- **Evidence:** `packages/engine/src/delve/rooms.ts:88` "command.members.length === 0"
- **Case:** An empty party, an oversized pack and a dead member are the only things the start refuses. Measured with a probe: it accepted an unknown approach (the delve then starts and `delveView` throws "must be a whole number: NaN", so the saved game cannot be drawn), the same member twice (two fighters share one id), Tactics of 1.5 and NaN, a drill bonus of 99,999 bp, a row called "middle", weapon rarity 9 and an unknown pack item. Today only the sample start calls it, so nothing reaches the player. Slices S3 to S5 let the player pick the party, gear and pack, and then this command is the only gate between a UI slip and a broken or over-geared delve.
- **Fix:** In `startDelve`, refuse duplicate members, an approach, row or armour weight not in the rules, a rarity outside the rarity list, a pack kind not in content, and Tactics or drill that are not whole numbers in range. One test per refusal.

### F2 AGENTS.md says "No deploys yet", but Vercel deploys every push, and the CI-05 override is not recorded

- **Rework if left:** medium
- **Effort:** S
- **Evidence:** `AGENTS.md:32` "No deploys yet."
- **Case:** Vercel builds production from `main` and a preview for every push to any branch (read from Vercel on 2026-11-09; D-167 chose this). Three things follow. A fresh session reads "No deploys yet" and skips CI-05's check that the deployed commit equals the merge commit. CI-05 says branch previews are off; D-167 turns them on, yet AGENTS.md "Overrides" says "None" and `.ai-master.json` has no override. And `vercel.json` has no ignore step, so a commit that changes only HANDOFF and the roadmap (D-194) rebuilds production, and each push to a working branch builds a preview; the last S2 branch had four previews in 17 minutes.
- **Fix:** Replace the AGENTS.md line with what deploys and from where. Record the CI-05 override (previews on, D-167) in AGENTS.md and `.ai-master.json`. Ask the owner whether docs-only commits should skip the Vercel build.

### F3 A failed save is silent

- **Rework if left:** medium
- **Effort:** S
- **Evidence:** `packages/ui/src/play/game.ts:136` "if (store) writeSave(store, game.state, savedAt);"
- **Case:** `writeSave` returns false when storage is full or blocked, as in a private tab on a phone. `saved` drops that result. The player plays a whole delve believing it is kept, reloads, and starts from nothing. The playtest (D-230) is on the owner's phone, so this can cost a playtest delve.
- **Fix:** Return the result from `saved` and show a "not saving on this device" notice once when it is false. A test with a store that throws.

### F4 No test checks that the gate 1 content resolves

- **Rework if left:** medium
- **Effort:** M
- **Evidence:** `packages/content/test` absent: searched gate1, gate1Text, gate1Content in packages/content/test
- **Case:** The gate 1 pack is tested only through the engine's delve tests. A wrong foe kind in a room, a class skill with no action, an Auto rule naming a missing action, or an id with no word in `gate1.en.json` fails only if a seeded test happens to walk that path; otherwise the player sees a raw id or a thrown error mid-delve. Two gaps exist now: the words file has `danger.routine`, `danger.hazardous` and `danger.perilous` but no `danger.deadly`, though the rules give `deadly` a difficulty; and nothing stops a class whose health less the Toughness pivot is 0 or below. Slices S3 to S6 add content fast, as data (GAME-04), which is when this pays.
- **Fix:** Add `packages/content/test/gate1.test.ts`: every referenced id resolves, every id has a word, every party member's starting health is at least 1, rarities are inside the list.

### F6 The save has no upgrade path, and a save from newer rules loads without a note

- **Rework if left:** low
- **Effort:** M
- **Evidence:** `packages/ui/src/play/save.ts:58` "save.version !== SAVE_VERSION ||"
- **Case:** Probed. A save with format version 2 is treated as unreadable: it is copied aside and a new game starts, so nothing is lost, but nothing can bring it back either. A save with rules version 99 loads with no notice and plays on under this build's rules. Neither can happen today (one format, one deploy). The first change to the state's shape, due in S3, makes every playtest save unreadable unless an upgrade is written then (GAME-05).
- **Fix:** When `SAVE_VERSION` first changes, add the upgrade step and a test with a version 1 fixture. Now: show a note for a newer rules version, as for an older one.

### F7 Auto finds its "once" rule by action id, not by the rule that fired

- **Rework if left:** low
- **Effort:** S
- **Evidence:** `packages/engine/src/delve/auto.ts:207` "const rule = classOf(state, actor).auto.find("
- **Case:** After Auto picks an action, `stepAuto` looks up the first rule with that action id to record its once-a-fight or once-a-round mark. It is correct for today's four classes. It goes wrong when a class has two rules for one action and only the later one is marked once (the mark is never recorded, so the rule fires every turn), and it records a mark when the plain-attack fallback happens to share an action id with a once rule. This is content a designer can write without touching code, and the 400-delve fuzz cannot see it. The same function spells the swap action as a literal where `SWAP_ACTION` exists.
- **Fix:** Return the rule with the choice from `autoRuleChoice` and record the mark only for that rule. Use `SWAP_ACTION`. One test with a two-rule class.

### F8 Haste and Guard can be spent on an ally who has already acted

- **Rework if left:** low
- **Effort:** S
- **Evidence:** `packages/engine/src/delve/actions.ts:300` "ally && isUp(target) && target.id !== actorId"
- **Case:** Haste moves the target to just after the caster. If the target has acted this round, the use is spent and nothing happens this round; the order change still holds for later rounds. The screen offers it without a word. Whether that is a wasted use or a fair order play is a design call for the owner, not a defect in the code.
- **Fix:** Either refuse Haste on an ally who has acted, or say on the preview that they act from that place next round.

### F9 Step 4's loader can overwrite an unreadable save

- **Rework if left:** low
- **Effort:** S
- **Evidence:** `packages/ui/src/step4/Step4.tsx:61` "localStorage.setItem(`${KEY}.unreadable.${Date.now()}`, text);"
- **Case:** If the copy aside throws (storage full), the catch reports "no save, not unreadable", a new game starts, and the next save replaces the unreadable one. The play page already solves this with `keepAside` and `mayWrite`. Step 4 is a kept prototype, so the cost is small.
- **Fix:** Reuse `keepAside` from `play/save.ts`, or leave it and note that step 4 is frozen.

### F10 Two tabs overwrite each other's save

- **Rework if left:** low
- **Effort:** M
- **Evidence:** `packages/ui/src/play/Play.tsx:86` "saved(next, storage(), new Date().toISOString());"
- **Case:** Each tab keeps its own game in memory and writes `play.save` after its own commands. The tab that moves last wins. Nothing listens for the storage event (searched `storage` listeners in `packages/ui/src`: none). On a phone this takes a duplicated tab, so it is rare.
- **Fix:** On a `storage` event for the save key, show "this delve moved on in another tab" and stop writing.

### F20 The boundary check flags names, not uses, and its command line is untested

### F22 Tools do not clean up when a step fails, and `--compare` always exits 0

- **Rework if left:** low
- **Effort:** S
- **Evidence:** `tools/balance/pool.ts:36` "worker.on('error', reject);"
- **Case:** When one career thread throws, the others keep playing their queue before the error shows. `tools/mockup-shot.mjs` and `tools/play-shot.mjs` close the browser only on the success path, so a thrown step leaves Chromium running, which the pkill lesson (×3) shows is costly to clear. And `tools/balance/run.ts --compare` prints "identical … 0 of 20" and exits 0, so it cannot stop an `&&` chain; today a person reads it, which is its documented use.
- **Fix:** Terminate the pool on first error; wrap the screenshot bodies in try/finally; add `--strict` to the runner if a chain should ever stop on a moved baseline.
